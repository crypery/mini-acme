# mini-acme

> [English version](README.md)

> [China version](README_CN.md)

**mini-acme** — утилита для автоматического управления сертификатами по протоколу ACME (RFC 8555), написанная на чистом C с использованием библиотеки **crypery** (HTTPS Library).

Для центра сертификации Let's Encrypt утилита запрашивает сертификат по протоколу ACME с использованием метода подтверждения владения доменом **HTTP-01**: на порту 80 отдаётся специальный файл валидации `/.well-known/acme-challenge/<token>`, который CA-сервер запрашивает по HTTP. Wildcard-домены (`*.example.com`) нельзя подтвердить через HTTP-01 — для них автоматически используется метод **DNS-01**: требуемая TXT-запись `_acme-challenge.*` либо публикуется и удаляется через API DNS-провайдера (`--dns <provider> --apikey <key>`, пока поддерживается `dynadot`), либо выводится для добавления администратором у DNS-провайдера; затем утилита ждёт, пока запись станет доступна в публичном DNS, и завершает заказ.

## Описание

При запуске mini-acme:

1. Создаёт (или загружает из кэша) ACME-аккаунт с ключом RSA-2048.
2. Запрашивает у Let's Encrypt сертификат RSA-2048 для одного или нескольких доменов: первый `-domain` — основной (CN + имя файла кэша), все домены перечисляются в расширении SAN.
3. Проходит подтверждение владения для каждого домена: обычные имена — через HTTP-01 (запускается HTTP-сервер на порту 80, отдающий файлы валидации; все остальные HTTP-запросы перенаправляются на HTTPS), wildcard-имена — через DNS-01 (публикуется требуемая TXT-запись — автоматически через API DNS-провайдера при заданных `--dns`/`--apikey`, иначе выводится для администратора — и ждёт, пока она станет видна в публичном DNS).
4. Сохраняет выпущенный сертификат (полная цепочка: лист + промежуточные) и ключ в каталог кэша и завершает работу — HTTPS-сервер не запускается.

Ключ аккаунта и выпущенные сертификаты хранятся в локальном каталоге кэша (по умолчанию: `certs/`): `<primary>.pem` (ключ + полная цепочка), `<primary>.crt` (полная цепочка), `<primary>.key` (ключ). При повторном запуске кэшированный сертификат переиспользуется, пока у него осталось более 30 дней срока действия **и** его SAN покрывает все запрошенные домены; иначе выпускается новый сертификат.

## Особенности проекта

- **Чистый C, без внешних криптобиблиотек** — весь TLS-стек (TLS 1.2/1.3, AES-128-GCM, SHA-256, HMAC-SHA256, HKDF, RSA-2048, ECDH P-256/X25519, X.509) реализован внутри библиотеки crypery.
- **Полный цикл ACME**: создание аккаунта, заказ сертификата на несколько доменов, валидация HTTP-01/DNS-01 для каждого домена и получение сертификата.
- **Мультидоменные (SAN) сертификаты**: `-domain` можно повторять до 8 раз (например, apex + `www`) — все имена попадают в один сертификат.
- **Wildcard-домены**: `*.example.com` подтверждается через DNS-01 (TXT-запись `_acme-challenge.example.com` публикуется и удаляется через API DNS-провайдера при `--dns <provider> --apikey <key>` — пока поддерживается `dynadot` — либо выводится для ручного ввода; утилита опрашивает публичный DNS, пока запись не станет видна, дважды подтверждает её и удаляет после валидации).
- **Полная цепочка сертификатов**: сохраняемые `.crt`/`.pem` файлы содержат лист и промежуточные сертификаты, поэтому браузеры строят цепочку без ошибок.
- **Кроссплатформенность**: Windows (Winsock2/WinAPI) и POSIX (BSD-сокеты, pthreads) — один и тот же исходный код.
- **Одноразовый режим**: получает сертификат и завершает работу — без демонов и открытых портов.
- **Кэширование**: повторный запуск не создаёт новый аккаунт и не запрашивает новый сертификат, пока кэшированный действует более 30 дней и покрывает все запрошенные домены; устаревший кэш (истёкший срок или отсутствующее имя в SAN) вызывает повторный выпуск.
- **Минимальные зависимости**: только стандартная C-библиотека, pthreads (POSIX) и zlib (gzip-сжатие в HTTP-модуле).
- **Staging по требованию**: по умолчанию используется продакшен-среда Let's Encrypt; для тестирования на staging CA (чтобы не расходовать лимиты продакшена) передайте `-dir https://acme-staging-v02.api.letsencrypt.org/directory`.

## Используемые модули

| Модуль | Назначение |
|--------|------------|
| **crypery** | Сетевой стек на чистом C: криптографический слой TLS 1.2/1.3 (`tls`), обёртка, совместимая с OpenSSL (`ssl`), HTTP/1.1-сервер (`http`) и HTTP/HTTPS-клиент (`url`). Все криптоалгоритмы реализованы с нуля; используются для ACME-запросов (клиент `url`) и генерации/подписи RSA-ключей (модуль `tls`). |
| **utilery** | Коллекция базовых C-библиотек: JSON-парсер (`json` — разбор ответов ACME-сервера), модуль логирования (`log`), модуль настроек (`sett`) и библиотека `ecma` (UTF-8 кодек, регулярные выражения, строковый буфер). Без внешних зависимостей. |
| **zlib** | Библиотека сжатия; используется модулем `http` crypery для gzip-сжатия ответов (необязательно, отключается флагом `HTTP_NO_GZIP`). |

## Компиляция

### Windows (build_acme.bat)

Требуется MinGW (gcc в PATH). Запустите:

```bat
build_acme.bat
```

Результат: `mini-acme.exe` в корне проекта.

### Linux (build_acme.sh)

Сборка выполняется внутри Docker-контейнера с gcc (образ `gcc:13`), поэтому на хосте нужен только Docker. Запустите:

```bash
bash build_acme.sh
```

Результат: бинарник `mini-acme` (ELF, x86-64) копируется в корень проекта.

Образ контейнера можно переопределить переменной окружения `IMAGE` (например, `IMAGE=gcc:14 bash build_acme.sh`).

## Использование

```
mini-acme [-domain <name>]... [-dir <acme-directory-url>] [-cache <dir>] [-email <addr>] [--apikey <key> --dns <provider>] [-h]
```

| Аргумент | Описание | По умолчанию |
|----------|----------|--------------|
| `-domain <name>` | Домен для включения в сертификат (повторяется до 8 раз; первый = основной: CN + имя файла кэша, все = SAN) | hostname |
| `-dir <url>` | URL ACME-каталога CA | Let's Encrypt production |
| `-cache <dir>` | Каталог кэша (ключ аккаунта, сертификаты) | `certs` |
| `-email <addr>` | Контактный e-mail ACME-аккаунта | `admin@example.com` |
| `--apikey <key>` | API-ключ DNS-провайдера (обязательно вместе с `--dns`); используется для автоматической публикации/удаления dns-01 TXT-записи | - |
| `--dns <provider>` | DNS-провайдер для автоматического управления TXT-записью (поддерживается: `dynadot`; обязательно вместе с `--apikey`) | - |
| `-h`, `-help` | Справка | - |

### Требования

- Каждый обычный домен должен быть **публично доступен** — его A/AAAA-запись должна указывать на машину, где запущена утилита; иначе HTTP-01-валидация не пройдёт.
- Входящий порт **80** (HTTP-01) должен быть открыт.
- Права на привязку к порту 80 (на Linux — запуск от root или с `CAP_NET_BIND_SERVICE`).
- Для **wildcard**-доменов: валидный API-ключ DNS-провайдера при использовании `--dns`/`--apikey` (иначе — право добавлять DNS TXT-записи у DNS-провайдера) и исходящий порт **53** (UDP, с автоматическим fallback на TCP — утилита опрашивает публичные резолверы 8.8.8.8 / 1.1.1.1 / 9.9.9.9, ожидая появления записи).

### Примеры

```bash
# Сертификат для example.com (по умолчанию: Let's Encrypt production)
mini-acme -domain example.com

# Apex + www в одном сертификате, staging-среда Let's Encrypt (для тестов)
mini-acme -domain example.com -domain www.example.com -dir https://acme-staging-v02.api.letsencrypt.org/directory

# Wildcard: выводит TXT-запись, которую нужно добавить у DNS-провайдера, и ждёт её
mini-acme -domain example.com -domain '*.example.com'

# Wildcard с автоматическим управлением TXT-записью через API Dynadot
mini-acme -domain example.com -domain '*.example.com' --dns dynadot --apikey <ваш-api-ключ>

# Свой каталог кэша и e-mail
mini-acme -domain example.com -cache /var/lib/mini-acme -email admin@example.com
```

### Пример сессии

```
Domains (2): example.com www.example.com
Obtaining certificate for example.com ...
Certificate valid until: 2026-12-20 12:00:00 UTC
Certificate saved to certs/example.com.pem
Done.
```

Программа завершает работу после получения сертификата. Чтобы принудительно выпустить новый (например, после добавления домена), удалите файлы кэша основного домена (`certs/<primary>.pem`, `.crt`, `.key`) и запустите снова.
